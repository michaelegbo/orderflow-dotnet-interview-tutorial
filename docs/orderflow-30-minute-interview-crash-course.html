C# foundations

Values, decisions, loops, and methods—the small pieces every program uses.

Simple picture

A program remembers information, makes decisions with it, repeats useful work, and gives names to reusable actions.

The four ideas

  • A variable is a labelled box: string customer = "Sarah";
  • A condition asks a yes-or-no question: if (paid).
  • A loop repeats work for several items.
  • A method gives a name to a job and can return a result.
What is really happening?

C# checks types when the program is built. Even var total = 75m; has a real type—C# works out that it is decimal. The program then runs statements in order. When it calls a method, that method receives its inputs, performs its job, returns a value if needed, and the caller continues.

Conditions often combine questions: && means both must be true, || means either may be true, and ! reverses true and false.

C# · one small order
string customer = "Sarah";
int quantity = 3;
decimal unitPrice = 25m;

decimal total = quantity * unitPrice;

if (total >= 50m)
    Console.WriteLine($"{customer}: £{total:F2}");

Why the $? It enables string interpolation: values inside { } are placed into the sentence. :F2 shows two decimal places.

Method shape: decimal CalculateTotal(int quantity, decimal price). The first word is the return type; the values inside the brackets are inputs.

Say this

“C# is strongly typed, so a variable has a known type. I use conditions for decisions, loops for repetition, and small methods to keep each job clear and reusable.”

Quick check: What type should hold £25.50?

Use decimal for money because it represents base-10 values accurately.

Remember: value → decision → repetition → method.

Objects, interfaces, collections, and LINQ

How OrderFlow represents orders and asks useful questions about groups of them.

Simple picture

An object keeps related information and behaviour together. An interface states what a helper promises to do. LINQ asks questions about groups of objects.

Object-oriented programming

  • A class is the design; an object is one thing created from that design.
  • Encapsulation protects an object's values by changing them through safe methods.
  • An interface is a promise. The caller knows what can be done without knowing the internal details.
  • Polymorphism means different objects can fulfil the same promise in their own way.
Why does this matter in OrderFlow?

An Order should protect rules such as “a cancelled order cannot be paid.” Code outside the object asks it to perform a valid action instead of changing Status freely. Meanwhile, IOrderRepository lets the service ask for storage without caring whether the implementation uses EF Core, memory, or something else.

Prefer composition when possible: an order uses services rather than inheriting a large collection of behaviour it may not need.

C# · domain and query
public interface IOrderRepository
{
    Task<Order?> FindAsync(Guid id);
}

public class Order
{
    public Guid Id { get; } = Guid.NewGuid();
    public decimal Total { get; private set; }
}

var largeOrders = orders
    .Where(order => order.Total > 100m)
    .OrderByDescending(order => order.Total)
    .ToList();
List<T>

An ordered group. Good when you visit items in sequence.

Dictionary<TKey,TValue>

Finds a value using a unique key. Usually fast for lookups.

Where

Keeps only items that match a condition.

Select

Changes each item into a new shape.

LINQ detail: many LINQ calls build a query plan. Work may not happen until you enumerate it with foreach or materialise it with ToList(). This is called deferred execution.

Say this

“I keep business rules inside domain objects, depend on small interfaces at boundaries, and use LINQ for readable filtering, projection, ordering, and grouping.”

Quick check: Which LINQ method keeps matching orders?

Where filters. Select changes shape; OrderBy changes order.

Remember: class = design; object = instance; interface = promise.

Async and core .NET

How a web server waits for databases and networks without wasting a worker.

Simple picture

await means: “Pause this job here, let the worker do something else, and continue when the result arrives.”

The important truth

  • An async method normally returns Task or Task<T>.
  • await does not automatically create a new thread.
  • Async is most useful for waiting on I/O: databases, files, HTTP, and queues.
  • A CancellationToken carries a polite stop request through the call chain.
  • Use Task.WhenAll when independent async operations can run together.
What happens at await?

The operation returns a Task, which represents work that may finish later. If it is incomplete, C# remembers where the method paused and returns control to the caller. The waiting thread is free for another request. When the task completes, the method continues from the saved point.

Exceptions are carried by the task and are thrown when it is awaited. Avoid async void except for event handlers because callers cannot await it or reliably observe its failure.

C# · async service
public async Task<Order?> GetOrderAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    return await repository.FindAsync(
        id,
        cancellationToken);
}

What .NET does with your code

The C# compiler changes source code into IL, a middle form stored in an assembly. The CLR runs the application. The JIT turns needed IL methods into machine instructions for the current computer.

Say this

“Async improves scalability for I/O-bound work because a thread does not need to sit idle while waiting. I pass cancellation tokens and avoid blocking with .Result or .Wait().”

Quick check: Does await always create a new thread?

No. Await normally releases the current thread while an I/O operation is incomplete.

Remember: async is about waiting efficiently.

ASP.NET Core Web API, EF Core, and DI

The path from an HTTP request to a saved OrderFlow order.

Simple picture

A request enters a line of checkpoints, reaches an endpoint, calls the business service, uses EF Core to speak to the database, and returns a response.

Request journey

  1. Kestrel receives the HTTP request.
  2. Middleware handles shared work such as errors, logging, authentication, and authorization.
  3. Routing selects an endpoint from the HTTP method and URL.
  4. Model binding turns route, query, and JSON values into C# inputs.
  5. The controller calls an application service. The service applies the use case.
  6. EF Core reads or writes SQLite, and the API sends an HTTP response.
How do you choose the response?

Use the HTTP result that describes what happened: 200 OK for a successful read, 201 Created after creating an order, 400 Bad Request for invalid input, 401 Unauthorized when identity is missing or invalid, 403 Forbidden when the known caller lacks permission, and 404 Not Found when the order does not exist.

Do not expose the EF entity automatically. A DTO lets the API return only the fields its contract promises, even if the database model later changes.

C# · minimal endpoint shape
app.MapPost("/orders", async (
    CreateOrderRequest request,
    IOrderService service,
    CancellationToken token) =>
{
    var order = await service.CreateAsync(request, token);
    return Results.Created($"/orders/{order.Id}", order);
});
DTO

The API's input or output shape. It keeps the HTTP contract separate from the domain object.

Validation

Rejects missing or invalid input before it can damage business state.

Authentication

Checks who the caller is.

Authorization

Checks what that caller may do.

EF Core

Turns C# database queries into SQL and rows back into objects.

Migration

A saved, repeatable change to the database structure.

Dependency injection

Instead of a controller building its own repository, it asks for IOrderService. The application setup chooses the real implementation. This makes dependencies clear and testing easier.

Lifetimes: Transient creates a new instance each time; Scoped normally creates one per web request; Singleton shares one for the application's lifetime.

EF Core detail: tracking remembers loaded entities so changes can be saved. For a read-only query, AsNoTracking() avoids that work. SaveChangesAsync() sends the tracked changes to the database as one unit of work.

Strong interview story · modernising a legacy .NET system

“I would not rewrite a working IIS application all at once. First I would map its routes, authentication, database dependencies, integrations, and current behaviour. I would protect that behaviour with tests, then place a modern ASP.NET Core Web API beside it.”

“IIS could remain at the front while we migrate one business capability at a time. For example, I would move Orders into a thin API endpoint, an application service containing the use case, and an EF Core data-access layer. Migrated routes would go to the new application; everything else would still go to the legacy application.”

“For every slice, I would test behaviour, security and performance, shift traffic gradually, monitor errors and latency, and keep a rollback path. Once no traffic depended on the old route, we could retire it safely.”

  1. Target: supported LTS .NET + ASP.NET Core Web API, not another version of .NET Framework.
  2. Hosting: Kestrel is the ASP.NET Core web server; IIS may remain in front or host the app in-process.
  3. Modern pieces: middleware, DI, async I/O, DTOs, validation, EF Core, modern authentication, tests and observability.
  4. Judgement: start as a modular application; create microservices only when independent scaling or deployment justifies them.
Remember: discover → protect → coexist → move one capability → route → observe → retire.

Technical anchors: incremental ASP.NET migration · IIS and Kestrel hosting.

Say this

“I keep controllers thin: receive HTTP input, call the use case, and translate the result into an HTTP response. Business rules stay in the domain/application layer, and EF Core stays behind an interface.”

Quick check: Which DI lifetime is normally used for DbContext?

Scoped. One context normally follows one web request and its unit of work.

Remember: middleware → endpoint → service → database → response.

SOLID, testing, architecture, and algorithms

The final ideas that help you explain why a solution is safe and able to grow.

Simple picture

Good architecture puts business rules in a protected centre, keeps replaceable tools around the outside, and proves important behaviour with tests.

SOLID without slogans

  • S — Single Responsibility: one class has one clear job.
  • O — Open/Closed: add new behaviour without repeatedly rewriting stable code.
  • L — Liskov: a replacement must keep the promises callers rely on.
  • I — Interface Segregation: give callers small interfaces containing only what they need.
  • D — Dependency Inversion: important business code depends on promises, not database or web details.
Clean Architecture in one picture

The domain contains business rules. The application layer coordinates use cases such as “create an order.” Infrastructure implements outside details such as EF Core. The API translates HTTP requests and responses. Dependencies point inward, so database and web changes do not rewrite the core business rules.

This is a direction rule, not a demand for dozens of projects. Keep the structure only as complicated as the application needs.

Testing levels

Unit test

Checks one small rule quickly, with outside dependencies replaced.

Integration test

Checks that real parts work together, such as routing, EF Core, and SQLite.

End-to-end test

Checks a complete user journey through the running system.

Test pyramid

Many fast unit tests, fewer integration tests, and a small number of valuable E2E tests.

System design in one minute

  • Start with requirements and expected traffic before choosing technology.
  • Keep API servers stateless so a load balancer can send requests to any healthy copy.
  • Use caching for repeated reads, queues for slow background work, and timeouts/retries for unreliable dependencies.
  • Make important create/payment operations idempotent so retries do not repeat the business action.
  • Measure latency, throughput, error rate, and saturation before scaling.

Algorithms: the interview pattern

Think before coding
// 1. Repeat the problem in your words.
// 2. Walk through a small example.
// 3. State a simple solution first.
// 4. Improve it with the right structure.
// 5. Test normal, empty, and edge cases.
// 6. Explain time and space cost.

Common tools: dictionary for fast lookup, stack for matching brackets, queue for first-in-first-out work, two pointers for ordered data, and a sliding window for neighbouring items.

Complexity: O(1) means the work stays roughly constant; O(n) grows with the number of items; O(n²) often means a loop inside another loop. State both time cost and extra memory cost, then explain the trade-off in plain language.

Say this

“I begin with the business requirement, keep domain rules independent, choose the simplest architecture that meets current scale, add observability, and evolve only when measurements show a real bottleneck.”

Quick check: What protects a create-order endpoint from duplicate retries?

An idempotency key lets the server recognise a retry and return the first result instead of creating another order.

Remember: simple boundaries, useful tests, measured scaling.

Your reusable interview answer

When you are asked about almost any technical choice, use this short structure:

Define it simply: “It is a way to…”

Explain why: “I use it when…”

Tie it to OrderFlow: “For example, in the order API…”

Name the trade-off: “The cost or risk is…”

Show judgement: “I would measure or test…”

Angular’s mental model

Components describe the screen; Angular keeps the template in step with state.

Simple picture

A component is a small screen controller. Its TypeScript class holds state and behaviour; its HTML template describes what the user sees.

The pieces to remember

  • A component combines a class, template and styles.
  • Interpolation displays a value: {{ customerName }}.
  • Property binding sends data into an element: [disabled]="saving".
  • Event binding reacts to the user: (click)="save()".
  • An input sends data parent → child; an output sends an event child → parent.
  • A directive changes behaviour or structure; a pipe changes a displayed value.
Standalone and dependency injection

Modern Angular uses standalone components for new code, so a component imports the directives, pipes and components its template needs. A service holds reusable work such as API access. Angular’s injector creates that service and gives it to the component, which keeps construction and testing under control.

A signal is a value Angular can track. Read it by calling it, update it with set or update, and use computed for a value derived from other signals.

TypeScript · a small standalone component
@Component({
  selector: 'app-order-count',
  standalone: true,
  template: `<button (click)="add()">
    Orders: {{ count() }}
  </button>`
})
export class OrderCountComponent {
  count = signal(0);
  add() { this.count.update(value => value + 1); }
}
Say this

“Angular builds the UI from a tree of components. Data flows into a component, user events flow out, services provide shared behaviour through DI, and signals or observable streams notify the view when state changes.”

Quick check: Which syntax handles a button click?

(click) is event binding. Square brackets bind a property.

Remember: class = state; template = view; binding connects them.

Services, HTTP, forms, and routing

How a screen receives an address, validates input, and talks to a Web API.

Simple picture

The router chooses the screen. The component manages the interaction. A service talks to the API. A form protects the shape of user input.

  • Router: maps a URL to a component; guards decide whether navigation is allowed.
  • Lazy loading: downloads feature code only when that route is needed.
  • Reactive forms: define controls and validation in TypeScript, which suits larger testable forms.
  • HttpClient: returns cold Observables; the request starts when something subscribes.
  • Interceptor: handles cross-cutting HTTP work such as an auth header or consistent error handling.
TypeScript · API service
@Injectable({ providedIn: 'root' })
export class OrderService {
  private http = inject(HttpClient);

  loadOrders() {
    return this.http.get<Order[]>('/api/orders');
  }
}
Where should logic live?

Keep view-only interaction in the component, reusable API work in a service, validation in the form and business truth on the server. A route guard improves navigation, but it is not security—the API must still authorize every protected request.

Say this

“I keep components focused on presentation and interaction, move API work into typed services, use reactive forms for predictable validation, and lazy-load route-level features to reduce the initial bundle.”

Quick check: Is a route guard enough to secure an API?

No. Browser code can be bypassed. The backend must authenticate and authorize the request.

Remember: route → component → service → API.

RxJS without the confusion

An Observable represents values arriving over time; operators describe what to do with them.

Simple picture

A Promise gives one future result. An Observable can give zero, one, or many values and can be cancelled by unsubscribing.

  • map changes each emitted value; filter keeps matching values.
  • tap performs a side effect such as logging without changing the value.
  • catchError replaces or rethrows a failed stream.
  • debounceTime waits for a quiet period; distinctUntilChanged ignores repeated values.
  • The async pipe subscribes for the template and cleans up when the view is destroyed.
switchMap

Cancels the previous inner subscription. Best for search or reads where only the newest result matters.

mergeMap

Runs inner work concurrently. Useful when every independent operation must run.

concatMap

Queues inner work in order. Useful when writes must happen sequentially.

exhaustMap

Ignores new triggers while one is active. Useful for preventing repeated submit/login clicks.

Who owns the subscription?

Prefer the async pipe when the template only needs to display an Observable. It owns the subscription and cleans it up with the view. If code must subscribe manually, tie its lifetime to the component—for example with takeUntilDestroyed—so a destroyed screen does not keep reacting or leaking memory.

TypeScript · search as a stream
results$ = this.search.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(term => this.api.search(term)),
  catchError(() => of([]))
);
Say this

“I choose the flattening operator from the concurrency rule: cancel stale reads with switchMap, run independent work with mergeMap, preserve order with concatMap, or ignore repeat triggers with exhaustMap.”

Quick check: Which operator suits type-ahead search?

switchMap discards the old search when the user types a newer one.

Remember: choose an operator by cancellation, concurrency, or order.

NgRx: predictable shared state

A controlled loop for important state shared by several parts of the application.

Simple picture

The component announces what happened. NgRx calculates the next state. The component observes the result. Side effects handle work outside the store.

  1. The component dispatches an action: an event such as “Load Orders”.
  2. An effect hears actions that need API or other external work.
  3. The effect dispatches success or failure.
  4. A pure reducer receives the old state and action, then returns a new state.
  5. A memoized selector reads or derives exactly what the component needs.
TypeScript · focused NgRx flow
// Component
store.dispatch(OrderActions.load());
orders$ = store.select(selectAllOrders);

// Reducer: never mutate the old state
on(OrderActions.loadSuccess, (state, { orders }) => ({
  ...state,
  orders,
  loading: false
}));
When should you use NgRx?

Use it when state is shared widely, changes through many events, needs traceability, or benefits from effects and selectors. Do not add it automatically to a small local form. Local component state or a focused signal-based service may be simpler.

Reducers must stay pure: no HTTP call, random value, mutation, or hidden side effect. Effects perform external work; selectors provide reusable reads.

Say this

“NgRx gives us unidirectional state changes: actions describe events, reducers calculate immutable state, selectors expose read models, and effects isolate API calls. I use it only when the application’s shared-state complexity justifies it.”

Quick check: Where should the API call happen?

Effect. Reducers calculate state; selectors read it.

Remember: action → reducer/effect → result action → selector → view.

Performance, testing, and rapid recall

How to show that you can build Angular features that remain understandable and reliable.

Simple picture

Optimise the work Angular repeats, split code the user does not need yet, and test behaviour at the smallest useful level.

Performance and reliability

  • OnPush makes update triggers more explicit; signals and the async pipe notify Angular when their values change.
  • Use a stable tracking key in repeated lists so Angular reuses the correct DOM nodes.
  • Lazy-load large routes, avoid heavy functions in templates, and measure bundle and runtime performance before optimising.
  • Use takeUntilDestroyed or the async pipe when manual subscriptions are needed.
  • Test pure services and reducers directly; test components for rendered behaviour; keep a few E2E tests for critical journeys.
Signal

Excellent for synchronous local state and derived UI values. Angular tracks reads precisely.

Observable

Excellent for asynchronous streams, cancellation, events, HTTP composition, and RxJS operators.

Component test

Proves bindings, interaction, validation and rendered output.

E2E test

Proves a small number of complete user journeys through the real app.

Signals and Observables are partners

A signal is often the simplest shape for current UI state. An Observable is often the better shape for events and asynchronous work over time. You can bridge between them when necessary; choose the model that makes ownership and updates easiest to understand.

Say this

“I begin with clear component boundaries, typed services and observable or signal state. I add NgRx when shared-state complexity requires a traceable event loop, then protect critical behaviour with focused tests and measure performance before tuning it.”

Quick check: What helps Angular reuse rows in a changing list?

A stable tracking key, normally the item ID, tells Angular which item is which.

Remember: clear boundaries, explicit state, measured optimisation.

Your 60-second Angular answer

Use this when they ask you to describe an Angular feature from end to end:

The router loads a standalone feature and its smart component.

The component gets state from signals or selectors and sends simple inputs to presentational children.

User events trigger a component method or dispatch an NgRx action.

A typed service or effect calls the Web API; RxJS handles cancellation, errors and composition.

The new state reaches the template through a signal or async pipe, and tests prove the important behaviour.
